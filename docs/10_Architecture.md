# Technical Architecture

## Stack (recommended)
- Mobile: React Native + Expo + TypeScript; Expo Router.
- Backend: Python + FastAPI, modular monolith.
- DB: Neon PostgreSQL.
- ORM/migrations: SQLAlchemy 2.x + Alembic (recommendation).
- Object storage: Cloudflare R2, private buckets and signed URLs where needed.
- Hosting: Render web service initially; background worker only when needed.
- Notifications: Expo push initially; provider abstraction.
- Payments: mock adapter first; gateway integration later after capability/compliance review.
- Maps: provider abstraction; compare Google Maps/Mapbox/OSM ecosystem, cost and geocoding/routing needs before selection.

## Repository strategy
Single monorepo, split-ready ([decision 0001](decisions/0001-monorepo.md)):
- `mobile/` — Expo app (own `package.json`, lockfile, `.env.example`, lint/test config)
- `backend/` — FastAPI API and Alembic migrations (own `pyproject.toml`, `uv.lock`, `.env.example`)
- `infrastructure/` — deployment configuration and scripts
- `docs/`, `assets/` — product and technical documentation, brand references

Later if warranted, add `admin/` (admin/provider web) as another independent top-level app.

Independence rules, so any app can later move to its own repository with `git filter-repo --subdirectory-filter <dir>`:
- No imports across app directories and no shared code package.
- No root-level JavaScript workspaces; `mobile/` is a standalone Expo project.
- The API contract is shared only through FastAPI's OpenAPI output. The mobile app generates its TypeScript types from it.
- Each app has its own CI workflow, triggered by path filters.

## Backend modular monolith
Modules: auth, users, pets, providers, clinics, services, availability, appointments, caretaker_requests, offers, bookings, payments, reviews, community, notifications, moderation, admin, storage, analytics.

Each module owns its schemas, services and repositories; modules communicate through service interfaces/events rather than cross-module SQL coupling.

## Runtime components
- Mobile client → HTTPS REST API
- API → PostgreSQL
- API → R2 via signed upload/download workflow
- API → push notification provider
- API → map/geocoding provider (client/API as appropriate)
- Worker (later) → notifications, reminders, cleanup, moderation tasks

## API style
REST with `/api/v1`, OpenAPI generated by FastAPI. Consistent pagination, filtering, error envelope, request IDs and idempotency for booking/payment operations.

## Security baseline
- JWT/session strategy with refresh-token rotation or provider-managed auth; evaluate OTP costs/abuse.
- RBAC plus ownership checks.
- Rate limits, validation, upload restrictions and malware/content scanning strategy.
- Private documents; signed URLs with short expiry.
- Audit logs for provider verification, moderation and admin actions.
- Secrets in environment/secret manager; no secrets committed.
- HTTPS, backups, restore test, observability.

## Booking concurrency
Use transactional slot reservation or locking; ensure no double-booking. Idempotency keys for booking/payment requests. Provider availability is not considered reserved until booking state is safely persisted.

## Data and location
Start with latitude/longitude and bounding-box/approximate filtering; evaluate PostGIS for distance queries. Location data should be minimized and user-controlled. Exact owner home addresses are shared only when necessary for confirmed services and with explicit consent.

## Environments
Local → dev → staging → production. Separate databases, storage buckets and secrets. Never test against production customer data.

## Architecture principle
Build a modular monolith, not microservices. Extract services only when measured scale/team/operational needs justify it.
